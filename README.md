# Передержка домашних животных

Приложение для гостиницы передержки домашних животных: веб-интерфейс
на Django и консольная версия, работающие с общими данными.

## Назначение
Приложение передержки домашних животных. Оно помогает
оформлять бронирования, проверять, можно ли принять питомца, подбирать ему
подходящее место и рассчитывать стоимость проживания.

## Технологии
1. Python 3.12;
2. Django 5.2: веб-фреймворк;
3. Django Template Language: шаблоны страниц;
4. HTML: разметка страниц;
5. CSS и Bootstrap 5.3: оформление страниц;
6. JavaScript: небольшое поведение интерфейса;
7. SQLite и Django ORM: реляционная база данных, модели и миграции;
8. JSON: исходные данные и хранилище консольной версии;
9. pytest и pytest-django: автоматизированные тесты;
10. flake8: проверка качества кода;
11. Django Admin: административная панель;
12. Django Debug Toolbar: анализ SQL-запросов при разработке;
13. Unidecode: транслитерация названий мест для адресов страниц;
14. Django Forms: формы фильтрации, бронирования и загрузки фото;
15. Pillow: проверка и хранение загруженных изображений

## Целевая аудитория
1. Владельцы кошек и собак, которым нужно оставить питомца на время отъезда
2. Администратор гостиницы, который принимает заявки и управляет бронированиями

## Предметная область
Передержка домашних животных. Владелец временно оставляет питомца в гостинице
на определённые даты. Гостиница принимает животных (учитываются вид,
возраст и наличие прививок), размещает питомца в месте подходящего размера
и берёт плату за каждые сутки проживания

## Основные сущности
1. Пользователь. Участник системы (имя, контакты, роль), от роли зависят права
   1. клиент (владелец питомца) оформляет бронирования для своих питомцев;
   2. администратор (сотрудник гостиницы) управляет местами, видит все заявки,
      подтверждает и отменяет любые бронирования
2. Питомец. Животное клиента (вид, возраст, вес, наличие прививок)
3. Место. Вольер или комната определённого размера (малое, среднее, большое)
4. Бронирование. Заявка на проживание питомца в конкретном месте на даты
   заезда и выезда

## Основные функции
1. Проверка допуска питомца (гостиница принимает кошек и собак
   от 3 месяцев с прививками)
2. Подбор места по весу питомца (малое, среднее или большое)
3. Расчёт стоимости передержки. Тариф за сутки, который зависит от размера
   места, число суток по датам заезда и выезда
4. Просмотр и отмена бронирований. Клиент работает со своими,
   администратор со всеми

## Возможности приложения

В веб-интерфейсе:

1. просмотр мест с фильтром по размеру и занятостью на сегодня;
2. поиск мест, свободных на выбранный период;
3. просмотр питомцев с фильтром «можно принять», поиском по кличке
   или имени владельца, проверкой допуска и подходящими местами;
4. просмотр бронирований со сроком, стоимостью и статусом: поиск,
   фильтры по статусу, размеру места, месту и датам заезда, сортировка
   и постраничный вывод;
5. статистика: выручка, загрузка мест, питомцы по видам, популярные места;
6. ближайшие заезды на главной странице;
7. переходы между связанными страницами: от места к бронированию,
   от бронирования к питомцу;
8. оформление бронирования через форму с проверкой даты, допуска
   питомца, размера и занятости места;
9. изменение и отмена активного бронирования;
10. загрузка фото места

В консольной версии:

1. просмотр мест, владельцев и питомцев;
2. добавление владельца и питомца;
3. поиск питомца по кличке или имени владельца;
4. проверка допуска питомца и подбор места по весу;
5. проверка занятости места на выбранные даты;
6. оформление бронирования с расчётом стоимости;
7. отмена бронирования с сохранением его в истории;
8. статистика по бронированиям, питомцам и местам

Добавление владельцев и питомцев на сайте пока выполняется через
административную панель.

## Django-проект и приложения

| Пакет | Назначение |
|---|---|
| `config` | настройки проекта и корневые маршруты |
| `homepage` | главная страница и общий каркас всех страниц |

Модель `User` описывает пользователя предметной области и не связана со

View-функции не содержат HTML. Они получают данные через менеджеры
моделей (`Room.objects`, `Booking.objects`), проверяют параметры запроса,
складывают результат в контекст и передают его в шаблон через `render()`.
Правила предметной области (допуск питомца, подбор места, стоимость)
находятся в методах моделей.

## Шаблоны

Общий каркас лежит в каталоге шаблонов уровня проекта, он подключён
в `settings.py` через `DIRS`:

1. `templates/base.html`: HTML-документ, Bootstrap, свой CSS, JavaScript,
   подвал и блоки `title` и `content`;
2. `templates/includes/navigation.html`: шапка с логотипом и навигацией

Каждая страница наследует каркас через `{% extends "base.html" %}` и
переопределяет блоки. Повторяющиеся фрагменты вынесены во включаемые
шаблоны и подключаются через `{% include %}`:

| Шаблон | Где используется |
|---|---|
| `rooms/includes/room_card.html` | список мест, подходящие места на странице питомца |
| `bookings/includes/booking_status.html` | список бронирований, страница брони, история питомца |
| `bookings/includes/booking_period.html` | период проживания везде, где выводится бронь |
| `pets/includes/acceptance_badge.html` | допуск питомца |
| `includes/pagination.html` | постраничная навигация списка бронирований |

Ссылки пагинации строятся тегом `{% querystring page=... %}`: он берёт
текущие параметры запроса и меняет только номер страницы, поэтому
поиск, фильтры и сортировка сохраняются при переходе.

В шаблонах используются:

1. `{{ ... }}` для вывода атрибутов объектов: `{{ booking.pet.owner.name }}`;
2. `{% for %}` с `{% empty %}` для списков и пустых коллекций;
3. `{% if %}` для статуса брони, занятости места и допуска питомца;
4. `{% url %}` с пространствами имён для всех ссылок;
5. автоматическое экранирование: кличка с HTML-тегами выводится как текст

Маршруты имеют пространства имён `homepage`, `rooms`, `pets`, `bookings`
(`app_name` в `urls.py`) и имена `list` и `detail`, например
`{% url 'rooms:detail' room.id %}`.

### Фильтры

| Фильтр | Пример | Назначение |
|---|---|---|
| `length` | `{{ rooms\|length }}` | количество мест, питомцев, бронирований |

| `capfirst` | `{{ pet.species\|capfirst }}` | вид с заглавной буквы |

## База данных и Django ORM

С ПР9 веб-интерфейс работает с базой Django `db.sqlite3` через модели и
ORM. База ПР7 `data/pet_boarding.sqlite` осталась источником исходных
данных: из неё данные переносятся в таблицы, которыми управляют миграции.
Прямых SQL-запросов в представлениях нет.

### Модели

| Модель | Приложение | Поля | Связи |
|---|---|---|---|
| `User` | `users` | `name`, `phone`, `role` (клиент или администратор) | обратная `pets` |
| `Room` | `rooms` | `name`, `slug`, `size` (малое, среднее, большое), `price_per_night` | обратная `bookings` |
| `Pet` | `pets` | `name`, `species`, `age_months`, `weight_kg`, `is_vaccinated`, `room_size` (`GeneratedField`) | `owner` на `User`, обратная `bookings` |
| `Booking` | `bookings` | `check_in`, `check_out` (`DateField`), `status` (`TextChoices`) | `pet` на `Pet`, `room` на `Room` |

```
User 1 ──→ * Pet 1 ──→ * Booking * ←── 1 Room
```

1. первичный ключ `id` Django создаёт сам;
2. все внешние ключи с `on_delete=PROTECT`: нельзя удалить владельца,
   питомца или место, пока на них ссылаются записи, история бронирований
   не теряется;
3. `related_name` задаёт обратный доступ: `user.pets.all()`,
   `room.bookings.all()`, `pet.bookings.all()`;
4. `CheckConstraint` повторяют ограничения ПР7 на уровне базы: размер места
   и роль из списка, положительные тариф и вес, выезд позже заезда;
5. `choices` и `MinValueValidator` проверяют значения ещё до записи;
6. `Meta.ordering` задаёт порядок по умолчанию, `verbose_name` подписи
   для административной панели

Методы моделей: `Room.is_suitable_for()` и `Room.cost_for()`,
`Pet.rejection_reason()`, `Pet.can_be_accepted()` и
`Pet.required_room_size()`, свойства `Booking.is_active`,
`Booking.nights`, `Booking.cost`, методы `Booking.cancel()` и
`Booking.complete()` с `save(update_fields=["status"])`. У всех моделей
есть `get_absolute_url()`, шаблоны и админка берут адреса страниц из него.

### Статусы бронирования

С ПР10 вместо признака `is_cancelled` у брони поле `status` с
перечислением `Booking.Status(TextChoices)`:

| Значение | Подпись | Занимает место | Входит в выручку |
|---|---|---|---|
| `active` | Активно | да | да |
| `cancelled` | Отменено | нет | нет |
| `completed` | Завершено | нет | да |

Переход выполнен тремя миграциями: `0003_booking_status` добавляет поле,
`0004_migrate_booking_statuses` (`RunPython`) переносит отмены в
`cancelled`, а остальные брони в `active`, `0005_remove_is_cancelled`
удаляет старое поле. Завершённым статус автоматически по дате не
становится: его ставит администратор действием в админке.

Менеджер `Booking.objects` построен на `BookingQuerySet`:

| Метод | Что возвращает |
|---|---|
| `active()`, `cancelled()`, `completed()` | брони с нужным статусом |
| `billable()` | все, кроме отменённых: для выручки и загрузки мест |
| `overlapping(check_in, check_out)` | активные брони, пересекающиеся с периодом |
| `with_related()` | `select_related("pet__owner", "room")` |

Методы работают и через обратные связи: `room.bookings.active()`.

`Booking.clean()` проверяет правила предметной области: выезд позже
заезда, допуск питомца, размер места и то, что место не занято другой
активной бронью. Эти проверки срабатывают в формах, в том числе в
админке. Массовые действия админки работают через `update()` и `clean()`
не вызывают, поэтому действие «Вернуть в активные» отдельно проверяет
занятость места и пропускает конфликтующие брони.

### Адрес места и вычисляемое поле

`Room.slug` строится из названия: `unidecode()` переводит кириллицу в
латиницу, `slugify()` готовит строку для адреса, в конце добавляется
`id` для уникальности, например «Вольер 1» превращается в `voler-1-1`.
Поле заполняется в `save()` один раз и при переименовании не меняется,
поэтому ссылки не ломаются. Существующие места получили slug миграцией
`0004_populate_room_slugs`, после чего `0005_room_slug_unique` сделала
поле уникальным.

`Pet.room_size` объявлено через `GeneratedField`: размер места по весу
вычисляет сама база выражением `CASE WHEN weight_kg < 5 ...`, столбец
хранится (`db_persist=True`) и пересчитывается при изменении веса. После
`save()` новое значение видно после `refresh_from_db()`.

### Контекстный процессор

`homepage.context_processors.site_info` добавляет во все шаблоны
название гостиницы `site_name`, число мест `rooms_count` и число
активных броней `active_bookings_count`. Они выводятся в шапке,
заголовке вкладки и подвале, главная берёт счётчик отсюда же.

### Миграции и перенос данных

| Команда | Что делает |
|---|---|
| `python manage.py migrate` | создаёт таблицы и применяет все миграции, в том числе миграции данных |
| `python -m db.inspect_source_db` | выводит структуру базы ПР7 и проверяет связи и форматы, ничего не меняя |
| `python -m db.import_sqlite_to_orm` | переносит пользователей, места, питомцев и брони через ORM с прежними `id` в одной транзакции |
| `python manage.py loaddata demo_bookings` | добавляет 12 демонстрационных броней разных статусов из фикстуры |

Перенос сначала очищает таблицы ORM, поэтому повторный запуск не создаёт
дублей. Даты из строк `ГГГГ-ММ-ДД` превращаются в `date`, числа 0 и 1 в
`bool`. Файл `db.sqlite3` в репозиторий не входит: после клонирования он
создаётся командами из раздела «Установка». Резервная копия
`data/pet_boarding_backup.sqlite` тоже не коммитится.

Файлы ПР7 `sql/schema.sql`, `db/database.py` и `db/import_json.py`
сохранены: они создают исходную базу из JSON, с которой работает
консольная версия и скрипт переноса.

### Запросы ORM

| Где | Выражение | Приём |
|---|---|---|
| список мест | `Room.objects.order_by("price_per_night", "name")` | сортировка по двум полям |
| список мест | `.filter(size=size)` | фильтр по одному условию |
| свободные места | `Booking.objects.overlapping(check_in, check_out)` | метод менеджера, несколько условий |
| свободные места | `Room.objects.exclude(id__in=busy.values("room_id"))` | `exclude()` и подзапрос |
| карточка места | `get_object_or_404(Room, slug=slug)` | один объект по slug, 404 |
| карточка места | `room.bookings.active().select_related("pet")` | обратная связь, метод менеджера |
| карточка места | `Booking.objects.overlapping(today, tomorrow).filter(room=room).exists()` | проверка наличия |
| список питомцев | `Pet.objects.annotate(owner_name=F("owner__name"))` | `annotate()` и `F()` |
| список питомцев | `.filter(species__in=..., age_months__gte=..., is_vaccinated=True)` | несколько условий, `in` |
| список питомцев | `.filter(text_search(q, "name", "owner__name"))` | поиск по двум полям, `Q` и `icontains` |
| карточка питомца | `Room.objects.filter(size=pet.room_size)` | фильтр по вычисляемому полю |
| карточка питомца | `pet.bookings.select_related("room").order_by("check_in")` | обратная связь |
| все страницы | `Room.objects.count()`, `Booking.objects.active().count()` | подсчёт в контекстном процессоре |
| главная | `.values("id", "check_in", pet_name=F("pet__name"), ...)[:3]` | `values()`, ограничение выборки |
| бронирования | `Booking.objects.with_related()` | две связи за один запрос |
| бронирования | `.filter(status=status)` | статус из `Booking.Status.values` |
| бронирования | `.filter(room__size=size)`, `.filter(room_id=...)` | поле связанной модели и внешний ключ |
| бронирования | `.filter(check_in__gte=date_from)`, `.filter(check_in__lte=date_to)` | диапазон дат |
| бронирования | `.order_by(*SORT_FIELDS[sort])` | сортировка из словаря допустимых полей |
| бронирования | `Paginator(bookings, 5).get_page(page)` | постраничный вывод |
| статистика | `Room.objects.annotate(bookings_count=Count(..., filter=Q(...)), stay=Sum(...))` | условная агрегация по группам |
| статистика | `Booking.objects.billable().aggregate(Sum, Avg, Min, Max)` | сводные показатели |
| статистика | `Booking.objects.aggregate(active_count=Count("id", filter=Q(status=...)), ...)` | число броней каждого статуса |
| статистика | `Pet.objects.values("species").annotate(Count("id"), Avg("weight_kg"))` | группировка |
| статистика | `User.objects.annotate(pets_count=Count("pets")).filter(pets_count__gt=1)` | условие на агрегат, аналог HAVING |
| статистика | `Room.objects.annotate(...).filter(bookings_count__gte=threshold)` | популярные места по порогу |

Создание, изменение и удаление: `bulk_create()` и `all().delete()` в
скрипте переноса, `Booking.cancel()` с `save(update_fields=...)`,
`QuerySet.update()` и `delete()` в тестах.

Поиск: в SQLite `icontains` не учитывает регистр только для латиницы,
поэтому помощник `db/search.py` объединяет через `Q(...) | Q(...)`
варианты запроса в разных регистрах. Запросы «барсик» и «БАРСИК»
находят «Барсик».

Проверка параметров: неизвестные статус, размер, место и поле
сортировки заменяются значениями по умолчанию, неверная дата или
перевёрнутый период выводятся сообщением и не применяются, неверный
номер страницы даёт первую или последнюю страницу. В `order_by()`
попадают только поля из словаря `SORT_FIELDS`.

## Административная панель

Адрес `/admin/`. Для входа нужна учётная запись Django:

```bash
python manage.py createsuperuser
```

Модель `users.User` описывает владельцев и администраторов гостиницы и
входа в админку не даёт: вход выполняется встроенной моделью
`django.contrib.auth`.

| Модель | Настройки `ModelAdmin` |
|---|---|
| `Room` | столбцы с числом активных броней через `annotate`, ссылка «открыть» на страницу сайта, `list_editable` для тарифа, фильтр по размеру, поиск по названию, `slug` только для чтения, inline броней |
| `User` | столбец с числом питомцев, фильтр по роли, поиск по имени и телефону, inline питомцев |
| `Pet` | столбцы допуска и `room_size`, фильтры по виду, размеру места и прививкам, поиск по кличке и владельцу, `autocomplete_fields` для владельца, inline истории броней |
| `Booking` | владелец, сутки и стоимость в списке, фильтры по статусу, размеру места и месту, `date_hierarchy` по дате заезда, поиск по кличке, владельцу и месту, `autocomplete_fields`, действия «Отменить», «Завершить», «Вернуть в активные» |

Общее для всех: `list_display_links`, `ordering`, `list_per_page = 20`,
`list_select_related` и `select_related` в inline против лишних запросов.
Приложения подписаны по-русски через `verbose_name` в `apps.py`, поля
имеют `verbose_name` и `help_text`, заголовки панели заданы в
`bookings/admin.py`. Поиск во всех списках идёт через
`CyrillicSearchMixin` из `db/search.py`, поэтому кириллица ищется без
учёта регистра.

## Формы

| Форма | Тип | Назначение |
|---|---|---|
| `BookingFilterForm` | `forms.Form` | поиск, фильтры и сортировка списка бронирований из GET-параметров |
| `BookingForm` | `forms.ModelForm` | создание и изменение брони: питомец, место, даты |
| `RoomPhotoForm` | `forms.ModelForm` | загрузка фото места |

Формы лежат в `bookings/forms.py` и `rooms/forms.py`, поля оформлены
классами Bootstrap через `widgets`, общий фрагмент
`bookings/includes/form_field.html` выводит подпись, поле, подсказку и
ошибки.

**Фильтрация.** `BookingFilterForm(request.GET)` превращает строки
запроса в дату, объект места и значения из списков. Поле с ошибкой
выводится сообщением и в фильтрации не участвует, остальные условия
продолжают работать. `clean()` проверяет, что начало периода не позже
окончания, а неизвестное поле сортировки даёт ошибку и не попадает в
`order_by()`.

**Создание и изменение.** `BookingForm` построена на модели `Booking`,
поле `status` в неё не входит: новая бронь всегда активна, а меняет
статус только отмена. Проверки:

1. `clean_check_in()`: заезд не в прошлом, для существующей брони
   неизменённая дата допускается;
2. `Booking.clean()`, которую `ModelForm` вызывает сама: выезд позже
   заезда, допуск питомца, размер места по весу и занятость места
   другой активной бронью;
3. при изменении бронь исключает себя из проверки занятости
   (`exclude(pk=self.pk)` в `Booking.conflicts()`)

Новая форма предлагает заезд сегодня и выезд завтра, ссылки
«Забронировать» на страницах места и питомца подставляют их в форму.
После сохранения выполняется перенаправление на страницу брони с
сообщением `messages.success`. Изменять можно только активные брони:
отменённые и завершённые дают 404.

**Отмена.** `booking_cancel` принимает только POST (`@require_POST`,
GET даёт 405), ищет бронь среди активных и вызывает `cancel()`: запись
остаётся в базе со статусом «Отменено», место освобождается.

**Загрузка фото.** `Room.photo` (`ImageField`, `upload_to="rooms/"`),
файлы хранятся в `MEDIA_ROOT = media/` и при `DEBUG` раздаются по
`MEDIA_URL`. Форма отправляется с `enctype="multipart/form-data"`, файл
приходит в `request.FILES`. Pillow проверяет, что это изображение,
`clean_photo()` ограничивает размер 2 МБ. Каталог `media/` в
репозиторий не входит.

Все POST-формы содержат `{% csrf_token %}`, без токена Django отвечает
403.

## Как запрос становится страницей
```
Браузер: GET /rooms/voler-1-1/
   ↓
config/urls.py: path("rooms/", include("rooms.urls"))
   ↓
rooms/urls.py: path("<slug:slug>/", views.room_detail)
   ↓
rooms/views.py: room_detail(request, slug="voler-1-1")
   ↓   get_object_or_404(Room, slug=...), room.bookings.active()
ORM: SQL-запрос к db.sqlite3, строки превращаются в объекты моделей
   ↓
context: room, is_free, bookings
   ↓   + site_name, rooms_count, active_bookings_count из контекстного процессора
   ↓
render(): rooms/room_detail.html, наследует base.html
   ↓
HTTP-ответ: HTML-страница с кодом 200 или 404
```

### Исключения
Ошибки оформления бронирования образуют иерархию. Любую из них можно
перехватить через общий класс `BookingError`.

```
BookingError
├── InvalidPeriodError      дата выезда не позже даты заезда
├── PetNotAcceptedError     питомец не проходит условия приёма
├── RoomNotSuitableError    место не подходит питомцу по размеру
└── RoomNotAvailableError   место занято на эти даты
```

## Взаимодействие объектов
```
Booking
├── pet  ──→ Pet
│            └── owner ──→ User
└── room ──→ Room
```

1. Питомец хранит объект своего владельца, а не его имя
2. Бронирование хранит объекты питомца и места, поэтому через него доступны
   их данные: `booking.room.name`, `booking.pet.owner.phone`
3. Место проверяет, подходит ли ему питомец: `room.is_suitable_for(pet)`
   обращается к методу питомца `required_room_size()`
4. Бронирование не считает стоимость само, а спрашивает её у своего места
   через `room.cost_for()`
5. Отменённое бронирование остаётся в списке и не блокирует место

## Функции над коллекциями
Операции, которые относятся к одному объекту, реализованы методами классов.
Операции над списками объектов остались функциями модулей:

1. поиск по идентификатору и по части имени;
2. сортировка и подсчёт по видам и размерам;
3. проверка доступности места среди всех бронирований;
4. создание и отмена бронирований;
5. отбор бронирований места и питомца;
6. статистика;
7. загрузка и сохранение данных;
8. ввод данных с проверкой

## Хранение данных
Данные хранятся в каталоге `data` в файлах JSON. В файлах записаны только
данные и идентификаторы связанных объектов, а приложение работает
с объектами.

При запуске `storage.py` создаёт объекты в таком порядке: пользователи,
места, питомцы со ссылкой на владельца, бронирования со ссылками на питомца
и место. Если связанный объект не найден, запись пропускается с сообщением.
При сохранении ссылки на объекты превращаются обратно в идентификаторы.
Если файл отсутствует или повреждён, программа стартует с пустыми данными.

Пользователь:

```json
{
    "id": 1,
    "name": "Иванова Анна",
    "phone": "+7 900 111 22 33",
    "role": "клиент"
}
```

Место:

```json
{
    "id": 1,
    "name": "Вольер 1",
    "size": "малое",
    "price_per_night": 800
}
```

Питомец:

```json
{
    "id": 1,
    "name": "Барсик",
    "species": "кошка",
    "age_months": 18,
    "weight_kg": 4.5,
    "is_vaccinated": true,
    "owner_id": 1
}
```

Бронирование:

```json
{
    "id": 1,
    "pet_id": 1,
    "room_id": 1,
    "check_in": "2026-10-01",
    "check_out": "2026-10-08",
    "is_cancelled": false
}
```

## Установка
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python -m db.import_sqlite_to_orm
python manage.py loaddata demo_bookings
python manage.py createsuperuser
```

## Запуск программы

Веб-версия, после запуска открыть http://127.0.0.1:8000/

```bash
python manage.py runserver
```

Консольная версия:

```bash
python main.py
```

## Запуск тестов
```bash
pytest -v
```

Тесты проверяют:

1. создание объектов и их атрибуты;
2. строковое представление и преобразование в JSON и обратно;
3. связи между объектами;
4. правила приёма питомцев и подбора мест;
5. правило доступности: второе активное бронирование места на те же даты
   запрещено, отменённое бронирование место не блокирует;
6. исключения при оформлении бронирования;
7. отбор бронирований места и питомца;
8. статистику;
9. базу ПР7: таблицы, внешние ключи, импорт из JSON;
10. модели Django: связи в обе стороны, `PROTECT`, ограничение периода,
    отмену и изменение записей, поиск по кириллице;
11. страницы: фильтры, поиск, сортировку по допустимым полям,
    пагинацию с сохранением параметров, ответ 404, сообщения об
    ошибках ввода, статистику без отменённых броней;
12. статусы и `BookingQuerySet`: `active`, `cancelled`, `completed`,
    `billable`, `overlapping`, завершённая бронь не занимает место;
13. правила `Booking.clean()`: период, допуск, размер и занятость места;
14. slug и `get_absolute_url`, вычисляемое поле `room_size`,
    контекстный процессор;
15. административную панель: страницы открываются, поиск по кириллице,
    действие «Вернуть в активные» не возвращает бронь на занятое место;
16. формы: преобразование GET-параметров, ошибки отдельных полей,
    запрет прошлой даты, занятое место, недопуск питомца, размер места,
    изменение брони без конфликта с самой собой, отмена только через
    POST, 404 при повторной отмене, CSRF, загрузка и проверка фото

Тесты ORM работают с отдельной временной базой, которую pytest-django
создаёт и удаляет сам.

## План развития
На следующих этапах я планирую:

1. регистрацию и вход пользователей, разные права клиента и администратора;
2. формы добавления питомцев для клиентов после входа;
3. разработку API;
4. контейнеризацию приложения

Сейчас бронировать, изменять и отменять брони может любой посетитель
сайта: разграничение прав появится вместе с входом пользователей.
